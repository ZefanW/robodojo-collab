# 勘误与实际踩坑记录

这份文档补充[完整上手指南](GETTING_STARTED_zh-CN.md)，供第一次拿到仓库的 GPT‑6/Codex 助手和贡献者排查问题。先按症状找条目，再回对应操作文档执行；不要把整页修复方法依次运行一遍。

**整理日期：2026-10-08；历史记录覆盖 2026-09-18 至 2026-10-08。** 历史条目来自维护者留存的环境/存储报告、失败日志、模型收据、原生动作 ACK 和归档回验；本次只复核已有记录与代码，没有重新启动 GPU 实验或付费模型。历史修复保留了当时的版本和适用条件，不等于新机器已验证可用。原始记录含私有会话、路径与账号信息，不随公共仓库发布。

“当前实现”指本仓库 portable runner 的行为；“当前限制”指尚未实现或尚未验证的能力。尤其注意：历史协调器曾有经过授权的同边界重试与恢复工具，**当前 portable runner 不自动追加付费重试，也不能直接使用那些私有恢复脚本**。

## 机器与环境

### E01. `nvidia-smi` 正常、大显存，不代表能生成 Isaac 相机图像

- **现象：** GPU 能做模型推理，但模拟器渲染初始化失败、缺少有效相机观察。
- **原因与范围：** 模型推理和 Isaac RTX 渲染是不同要求。NVIDIA 的 [Isaac Sim 5.1 要求](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html) 明确不支持没有 RT Core 的 GPU，例如 A100/H100；不能凭 A800 的显存或 CUDA 可用性认定兼容。
- **处理：** 在实际模拟器机器上核对 GPU、驱动、系统和该版本的 compatibility checker。必要时把模型推理与受支持的 RTX 模拟器分开部署；macOS 可以做控制器，不能据此当作本项目的原生模拟器。
- **确认：** 兼容性报告、实际初始化日志及三路有效原生图像齐全。仓库的空闲显存检查只是资源门禁，不是渲染兼容性认证。见 [ENVIRONMENT.md](ENVIRONMENT.md)。

### E02. “换到 Sim6 就能跑”会改变复现条件

- **现象：** 某版本能启动，换一个任务却出现缺少类、资产或物理接口；有人准备统一升级所有任务。
- **历史记录，2026-09-18：** 留存报告记载 Sim5.1 在当时 RTX 3090/595.58.03 驱动组合中启动崩溃，换用 Sim6 后又缺少 `SingleClothPrim`。这是特定环境中的观测，不证明该驱动在所有环境都不兼容；能绕开一种启动故障的版本也不一定支持全部任务。
- **处理：** 当前基线按[固定映射](../registry/simulator-mapping.json)选择版本：23 个任务用 Sim6，31 个用 Sim5.1。按选定任务检查其原始版本和依赖；不要临时换版本后仍登记成同一基线。
- **确认：** manifest、任务映射、实际运行时版本一致；确需改环境时先定义可区分的新协议。历史“不支持”记录不等于这个任务永远不可运行，也不代表这次执行结果是零分。

### E03. `import websockets` 通过，服务仍报 `No module named 'websockets.asyncio'`

- **历史实测，2026-10-08：** 新增模拟器环境的 `websockets==12.0` 缺少策略服务使用的 `websockets.asyncio` 接口；单测顶层包导入没有覆盖到它。
- **当时处理：** 与参考环境逐项比较后，仅将这个包调整为 `15.0.1`，使用 `--no-deps`，没有批量升级整个环境。
- **你的下一步：** 在**实际启动服务的解释器**中检查所需接口，而不是只在控制器或另一个虚拟环境查包。这个历史版本修复仅适用于对应的 Sim6/策略组合，不是全版本通用安装指令。
- **确认：** `websockets.asyncio.server` 与实际客户端接口能导入，随后才检查原生启动。仍需保留 E06 所述的依赖冲突记录。

### E04. `CXXABI_1.3.15 not found` 可能来自继承的库覆盖

- **历史实测，2026-10-08：** Python 3.12 的 SQLite → ICU78 链依赖新 C++ ABI；启动配置强制预载的系统 `libstdc++.so.6.0.30` 不提供所需符号，原生初始化期间失败，尚无模型请求或原生动作。
- **当时处理：** 只把该任务的 `LD_PRELOAD` 指向环境中已经存在的兼容 `libstdc++`；保留原配置与失败现场。随后 SQLite、Torch、cuRobo 和 WebSocket 的 CPU 导入检查通过。
- **你的下一步：** 检查当前解释器、实际解析到的库和任务级启动配置。不要复制另一台机器的 `LD_PRELOAD`；不要自动替换系统 glibc、系统库或驱动。
- **确认：** 同一解释器、同一启动环境里的相关导入通过；单独开一个“干净终端”成功不证明原启动器已修好。不要把完整环境变量贴到公开 issue。

### E05. 装了视频 Python 包，仍找不到 `ffmpeg`

- **历史实测，2026-10-08：** 原生初始化报 `FileNotFoundError`，因为启动进程的 PATH 找不到 `ffmpeg`，即使环境里已有 imageio-ffmpeg 的可执行文件。
- **当时处理：** 将已有的 ffmpeg 7.0.2 可执行文件接入项目专用可执行目录，并核对其 SHA 与参考环境一致；没有重新下载。也检查了 Ninja，但没有证据表明 Ninja 当时发生过同样故障。
- **你的下一步：** 核对原生启动器实际看到的 PATH、`ffmpeg` 位置和版本；交互终端中能找到不等于 SSH/后台进程能找到。
- **确认：** 正确程序能被同一启动方式找到，并有实际视频输出和原生动作证据。那次运行没有依赖 `ffprobe`，不要把缺少它自动当成相同故障。

### E06. `pip check`、版本号、导入与真实运行证明的是不同事情

- **历史实测，2026-10-08：** 新旧环境的主要版本、IsaacLab/cuRobo Git HEAD 与检查的入口 SHA 一致，仍出现 E03–E05；Python 小版本和模块实际来源路径并不完全相同。
- **剩余限制：** 修复后参考环境和新增环境的 `pip check` 都仍非零。例如 IsaacSim kernel 6.0.0.1 声明 WebSockets 12.0，而策略接口需要更新的 API；不能声称整个依赖解析已干净。
- **处理：** 同时保留包版本、冲突报告、模块实际路径、关键源码 SHA、启动配置和实际运行证据。先定位冲突是否影响当前路径，再做针对性处理；不要看到冲突就一键升级/降级所有包。
- **确认：** 分别报告“声明冲突仍存在”“关键接口通过”“原生动作已发生”。新机器的完整安装流程仍未由本版本验证，不能把历史成功变成通用保证。

### E07. 主机内存、容器配额和磁盘峰值不能互相代替

- **现象：** `free` 看起来充裕却 OOM；有空闲 GPU 但多个初始化进程争内存；磁盘主要被轨迹和重复图像占满。
- **原因：** 容器 cgroup 限额可能小于宿主机；当前 portable runner 没有跨贡献者的全局资源调度器。2026-09-18 的存储审计摘要记录，轨迹压缩包、NPZ、重复 Base64/图像副本远大于 MP4；旧收集代码也会同时保留压缩包和解压副本。这是历史占用，不是当前磁盘测量。
- **处理：** 在实际目标机核对可用显存、cgroup 配额/用量、自己进程的占用和目标文件系统余量。把下载、解压、收集、导出 TAR 及临时副本一起算入峰值；不要先删视频或他人文件来腾空间。
- **确认：** 按当前并发与实际目录计算有余量。历史机型、核数、空闲容量和并发数不是新机器的默认值；即使认领的是不同任务，也不能忽略共享物理资源。

## 客户端、登录与额度

### E08. `thread/start` 接受模型名，不等于该客户端能生成

- **历史实测，2026-10-07：** 0.153.4 接受 `gpt-6.1-sol` 的建会话请求，但实际生成报告该模型不支持当前 ChatGPT 客户端路径。只看建会话成功会误报“已经跑通”。
- **当时处理：** 在明确授权的 Sol 实验中，保留完整、签名可核验的 0.159.2 客户端包，继续原线程和原场景；未重建历史。首次被拒请求的费用仍记未知，并公开客户端差异。
- **当前边界：** 本仓库 Astra 基线仍固定 **0.153.4 / Astra medium**。不能把 Sol 的修复直接套成 Astra 自动升级，也不能换 API key 或账号试到能用为止。
- **确认：** 版本与执行文件 SHA、实际授权回复、原线程及原生 ACK 对上。不要为了探测权益单独发付费请求；目录列表或会话建立只能作为准备证据。安装步骤见 [ENVIRONMENT.md](ENVIRONMENT.md)。

### E09. 日常 Codex 已登录，实验控制器仍提示缺少认证

- **原因：** 桌面应用/钥匙串登录与配置指定的 `controller.auth_home/auth.json` 不是同一个凭据来源；实验客户端也不是你日常助手的全局客户端。
- **处理：** 按环境文档用独立认证目录和固定客户端完成自己的文件式登录。核对配置里的绝对路径、文件存在性与账号身份散列即可，不输出令牌或整个认证文件。
- **另一个当前陷阱：** 云盘登录/认领 token 路径检查还会拒绝当前工作目录的后代。若从个人主目录执行，默认配置子目录可能被拒；从协作仓库根目录运行，并把 token 放在仓库外的权限 `0600` 文件中。
- **确认：** 运行者、解释器、固定客户端和认证目录都正确。登录成功不证明额度证据已可用，继续看 E10。

### E10. 已登录却 `Fresh passive allowance unavailable`，不是必然没额度

- **当前限制：** runner 在创建模型 app-server 前就检查额度，但没有附带首次被动快照采集器。当前原生通知还可能缺少它要求的账号身份字段；这是实际兼容性缺口。
- **处理：** 按 [QUOTA.md](QUOTA.md) 使用可信、账号绑定、仍新鲜的被动证据，并记录账号所有者确定的保留额度。不能给匿名事件补猜测身份、刷新旧时间戳、写入假余额，或付费调用来“刷新额度”。
- **历史教训：** 网络故障后快照过期曾使协调器退出，但后来核对并非额度耗尽。区分“用量证据不可用”和“已证实用尽”；共享账号的其他任务也会消耗额度。
- **确认：** 身份匹配、原始时间与有效期通过、已用/剩余口径正确、停止条件明确。若拿不到兼容证据，完成离线准备并报告此阻塞，不能承诺首次付费运行已打通。

## 分配、路径与初始化

### E11. 认领命令失败后重跑，提示 token 已存在

- **当前实现：** `git-claim acquire` 先创建本地 token，再尝试 Git 操作。因此网络/推送失败不证明远端没有认领；重复 acquire 不是幂等恢复。
- **处理：** 保留原 token，读取原权威分支的同一 work_id，对照 owner、token hash、run_id 与绑定。远端已成功就继续原认领；缺失或不确定时走受审查的核对流程。
- **不要：** 删除 token、生成新 token、另起 work_id 来避开冲突；不要把 token 内容放到 PR。
- **确认：** 权威分支中的身份与本地原 token 匹配，再进入执行。完整命令与读取方式见 [CLAIMS.md](CLAIMS.md)。

### E12. Fork 里认领成功，主仓库仍不允许执行；合并后又过期

- **当前实现：** Fork 记录是认领提案，须合入上游 `work-claims` 并回读才成为上游分配。租约从 acquire 时开始，最长 86,400 秒，没有自动续期；PR 等待时间也会消耗租期。
- **处理：** 认领 PR 去 `work-claims`，结果 PR 去 `main`。执行配置指向同一个权威上游；提前安排文档规定的续期/审查，不把 PR 合并时间当新的起点。
- **过期时：** 停止新调用，保存原场景，核对是否已有动作及是否有新 owner。过期不是自动接管许可；即使声称从未启动，也需有对应证据。
- **确认：** 回读的 status、owner、token hash、run_id、execution hash 与有效期全部符合当前执行。示例 accepted-assignment 文件本身不是权威分配。

### E13. 换目录或机器后，同一配置不能继续；准备脚本拒绝重复运行

- **当前实现：** 执行绑定包含机器化名、解析后的原生 output_root 与 run_id。JSON 中的路径不是 shell 表达式，`$HOME` 不会自动展开，相对路径也可能落在错误工作目录。
- **处理：** 用真实绝对路径；在模拟器主机用它自己的配置取得 `binding-info`。保留已接受的原路径和配置；迁移需要核对，不能只改机器名或目录就继续原认领。
- **源码准备：** `prepare_native` 面向固定、干净的副本，准备后会产生预期修改；再次运行可能因目录/修改已存在而拒绝。核对是否已经准备完成，不对正在使用的源码执行强制 reset 或重打补丁。
- **确认：** 控制器 transport.root 与模拟器 output_root 相同；两台机器共享同字节任务包，但认证只留控制器。源码 SHA、补丁和实际入口都符合锁文件。

### E14. `Native run directory exists`；启动失败但目录已生成

- **当前实现：** 任务包使用独占创建，native-start 拒绝复用已有 run 目录，以免无意重跑。存在目录既不证明成功，也不证明可以删除重建。
- **历史实测，2026-10-08：** 三次环境启动失败逐次保留；确认各次没有模型请求或原生动作后，才对核验过身份的自有子进程进行针对性修复，GPU 心跳始终保留。
- **处理：** 查原请求、付费收据、线程、原生进程与 ACK。已有动作走同一场景恢复；零启动也先留下证据并复核修复范围。当前 portable 没有一条自动清空重启命令。
- **确认：** 原实验现场和失败成本未丢失，只有一个合法控制器。不要删除目录、修改锁文件或换 run_id 来绕过保护。

<a id="recovery"></a>
## 中断、收据与恢复

### E15. 断网后机器人停了，但模型回复其实已经付费生成

- **历史实测，2026-10-08：** 有完整回复已经保存在控制器、远端 mailbox 尚未收到的情况。一次批量核对在 2,027 份完整收据中找到 22 份未送达，只补送原回复，没有重新请求模型。
- **处理顺序：** 核对原 owner/进程 → 原 thread 与场景 → 本地完整收据 → 远端收据及 SHA → 原生执行 ACK。已执行就不重发；确定未送达且边界一致才交付原收据；状态未知保持 hold。
- **当前入口：** 已获恢复原任务授权后，按 [RUNNING.md](RUNNING.md) 使用 `reconcile` / `resume`。`reconcile` 可能补送回复并产生机器人动作，不是只读 status。
- **确认：** 同一个边界的本地/远端原始收据匹配，原 ACK 正确推进，没有第二次付费生成或重复执行。SSH 断开本身不说明远端模拟器、tmux 或模型线程已停止。

### E16. HTTP 502、TLS 断开、900 秒超时，不足以判断可以重试

- **历史实测，2026-10-08：** 一次 502 发生在**交付已生成回复**时，靠补送修复；另一次连接中断并触发 900 秒等待超时，有证据表明原生成没有输出，才使用了单独授权的同边界重试。
- **原因边界：** 502 是中间服务/传输症状，不证明根因就是代理；这次记录没有确定其底层根因。其他时段的 TLS 错误也不能直接归因到某个超时轮次。
- **处理：** 先分清“生成失败”“交付失败”“ACK 未确认”。保留所有失败费用和不确定用量。不要关闭 TLS 校验、随意切换 provider，或把语义错误 400/403/409 当成临时网络错误无限重试。
- **确认：** 修复的是具体故障层，原线程、原历史、原场景与工具约定保持一致。历史的传输包装器仅作用于其受控 mailbox，不是给所有 API 的通用重试策略。

### E17. `serverOverloaded`、空输出不能一律自动再来一次

- **历史实测，2026-10-08：** 两次容量故障先确认原生场景未推进、原线程无输出、远端没有已执行回复，再在原线程/同一边界使用已授权的有限重试；失败用量未知仍保留未知。
- **当前限制：** portable runner **零次自动追加付费重试**。历史流程“最多额外两次”是具体实验授权，不是本仓库所有账号的默认权限。
- **处理：** 保存错误、时间、原边界、收据/ACK 与用量状态，报告是否已有执行及额外成本的不确定性，再由该任务的授权范围决定处理。未知交付、拒绝或缺失历史不应按普通容量故障处理。
- **确认：** 重复尝试若另获授权，也不能替换已成功/低分结果、重开线程或删除原失败账目。

### E18. 直接重启整个批次，会重复付费或破坏可恢复的场景

- **现象：** 控制器退出，但远端场景与工作进程仍存活；旧 process/hold 文件仍在，容易被误认成当前故障。
- **处理：** 对照当前进程身份、锁、请求和新 ACK，区分旧快照与现状态。先确认唯一 owner，再恢复原会话；有历史缺口、线程不一致或未知动作时停止，不靠重建上下文“补回”。
- **暂停：** 使用运行文档的 pause.request 流程，等正在处理的边界落盘；不要默认 Ctrl-C 等价于完整保存。只恢复已授权的原任务，不顺带复活用户暂停的其他队列。
- **确认：** 原 scene/thread/claim 保留、没有两个控制器争同一 mailbox，GPU 心跳和他人进程保持原状。某次历史恢复成功不意味着所有退出状态都能直接 resume。

### E19. 归档超时不是策略失败，不能重跑实验修文件

- **历史实测，2026-10-07：** 完成场景的文件传输/归档超时，后来只修复文件交付并完成 SHA 回验；没有重新运行模型或重置场景。
- **处理：** 保留原生终止与全部费用，查源文件是否完整、传输是否留下半文件、源目录是否仍变化。修复收集/传输，旧错误保留并以新的成功回验记录说明其已解决。
- **确认：** 源端与接收端的成员清单、字节数、SHA 一致，原结果与成本未变化。当前 collect 使用前后哈希检查；失败先查文件稳定性和 rsync/路径条件。
- **下一步：** 见 [EXPORT.md](EXPORT.md) 和 [STORAGE.md](STORAGE.md)，不要用重新实验来获取“更干净”的输出包。

<a id="results"></a>
## 完成、动作与统计口径

### E20. 视频看似成功、有 `_result.json`，都不是完整终止证明

- **现象：** 抓住/放下了物体却得零分；进程退出、有视频或部分结果，导出器仍拒绝 complete。
- **原因：** 原生任务可能还要求顺序、目标区域、释放/稳定或机械臂回位。启动、动作发生和原生完成是不同状态；界面中的部分分数也不能代替正式终止。
- **处理：** 对照任务说明与原生反馈，不凭画面改分。审查完成状态时，需要 native result、episode_complete、最后动作 ACK/控制步数一致，且没有未解决的初始化无效状态。当前校验器会核对终止 ACK 与结果控制数，但不会独立替你比较最后一条 `action_complete` 的控制数；审查者仍须核对实际动作记录。
- **确认：** 缺少哪个证据就报告哪个；未完成/无效保持对应状态，不能手改 manifest 为 complete。score 在 manifest 中为 0–1，网页展示为 0–100，避免重复乘 100。

### E21. cap20、100 次决策、模型响应数、原生控制步不是同一单位

- **当前协议：** 每次 `move_eef` 保留原规划/时间处理，只执行最多 20 个原生控制步的前缀；超出后缀丢弃，再观察。较短计划不补满 20，也不能偷偷继续执行丢弃后缀。
- **现象：** 一次决策包含多步动作；实际模型响应可能因会话机制多于外层决策。某些任务还有原生观察阶段，控制数不应简单等于决策数乘 20。
- **处理：** 分别记录计划长度、执行前缀、原生 ACK、决策数、真实响应/尝试次数。100 是决策上限；`--once` 是控制器边界限制，既不是一步物理动作，也不是固定 token 费用。
- **确认：** 以实际执行前缀与 ACK 为准。新启动时还没有 pending，`--once` 可以无事返回；退出码为零并不证明产生过一次回复。

### E22. cache 重复相加、失败当零费用，会让对比失真

- **当前口径：** cached input 是总 input 的子集；总 tokens = input + output，不能再加一次 cache。未缓存 input = input − cached input，前提是两个字段都确知。
- **历史教训：** 被拒请求、网络/容量故障可能没有完整 usage。unknown 应为 null，不是 0；恢复目录中的收据副本也不是第二次付费调用。
- **处理：** 保留每次实际尝试，只对同一次付费调用的收据副本去重；同一请求 SHA 下的真实重试仍是独立 attempt，不能按请求 SHA 合并费用。分开成功回复、未知用量和恢复开销，不要把账号共享余额变化直接当作该单个实验的美元账单。
- **确认：** 成本审计能追溯全部尝试，并明确已知总量与未知部分；模型、客户端、上下文和模拟器不同的结果不能只凭一个总 token 比例归因。

### E23. 重复同一布局、部分面板与真正的新场景不能混算

- **当前协议：** 官方 seed 目录是 0/1/2；layout ordinal 是该目录内实际布局的序号，另有资产 SHA。GPT 采样随机性不等于换了场景，重复同 SHA 也不是新几何。
- **处理：** 使用[场景目录](../registry/scenes.json)和任务包，不造 seed3、不遇缺失布局就改随机布局。结构性缺失、未开始、运行中和原生零分分开记录。
- **确认：** 完整 54 项比较使用五能力等权，Generalization 的标准/随机部分各占一半；不是简单平均所有行。部分面板不补零，单个样本的样本标准差不能写成已知 0。
- **当前样例：** 网页的四条历史记录都是 `solve_equation` 的同一个 seed0/layout0，用于验证交付链路，不是四个独立场景，也不是完整排行榜。详见 [PROTOCOL.md](PROTOCOL.md)。

## 导出、云盘与公开交付

### E24. 带点的 run_id 导出成意料外的文件名；重复导出拒绝 TAR

- **当前限制：** 导出器使用 `Path.with_suffix(".tar")`；`demo.v1` 和 `demo.v2` 都可能落到 `demo.tar`。以后新建身份优先用连字符；已经认领/发布的身份不要为绕过冲突而改名。
- **处理：** 始终读取 export 输出 JSON 中的 `archive.file`，不要自己拼 `RUN_ID.tar`。不同导出可使用分开的 destination 父目录，先核对目标是否已存在；相同 run 的已有完整归档应核验复用。
- **重复执行：** `--tar` 不覆盖已存在 TAR。若用 `> summary.json`，shell 会先截断这个文件，即使随后命令失败；新的尝试把诊断输出写到新的私有文件，不覆盖唯一有效摘要。
- **确认：** 摘要是有效 JSON，路径、归档大小和 SHA 对上；“目录存在”与“归档完成”不是同一证明。见 [EXPORT.md](EXPORT.md)。

### E25. `import --store results` 把大文件复制进了公开目录

- **当前实现：** import 为完整证据导入，会复制全部 allowlist 文件；不是仅登记一个 manifest。
- **处理：** 导入到 `.private/verified-results` 做完整检查，然后只复制不可变 `manifest.json` 到 `results/RUN_ID/`。图片、视频、轨迹和公开审计包走云盘，私有会话不公开。
- **同 ID 冲突：** 相同 manifest 可幂等返回 already_present；改变过的 manifest 不能覆盖原尝试。只有实际授权的新重复实验才生成带 lineage 的新身份；更新 URL 使用 storage overlay。
- **确认：** PR 中没有视频/原始会话；`--manifest-only` 仅用于后续索引构建，不替代首次字节、SHA 和原生证据校验。

### E26. CLI 上传返回成功，但别人仍下载不了

- **当前实现：** `storage publish` 的成功退出、`verification: remote_sha256` 可以只代表**登录状态下**下载回验成功。公开探测失败时仍可能返回有效收据，但 `public_download_verified=false`、download_url 为空。
- **处理：** 分别检查登录下载与不带账号凭据的公共下载；分享页、文件下载地址和播放器 URL 是三种不同能力。不能把需要自己的登录才能访问的链接标成公开可用。
- **确认：** 公共回验标志为 true、公共探测 SHA 匹配、download_url 非空，才登记为已验证公开下载。`playback_candidate` 还需浏览器实际播放/跳转验证，才可填写 playback_url。
- **CLI 优先：** 清华云盘的配置、上传、下载回验按 [STORAGE.md](STORAGE.md) 执行；账号授权和实际浏览器播放确认是不同环节，不需要为上传反复改用网页。

### E27. TAR 已上传，网页每个文件仍没有链接

- **原因：** 整包 TAR 的 SHA 与包内每张图片/视频的 SHA 不同；只登记 TAR 不会自动产生所有成员的文件位置。
- **处理：** 归档收据放 `bundles[run_id]`，每个成员按自身 SHA 放 `artifacts`，记录 bundle_sha256 与 bundle_member；单独上传的视频使用它自己的已验证收据。按存储文档合并后，以 `--storage registry/storage.json` 重建索引。
- **当前行为：** 同一 run 的不同归档 SHA 冲突会停止合并。文档示例允许把这个归档的成员下载记录提升为经过验证的独立文件记录；其他已有位置保留，不自动被新 URL 替换。其余链接更换需要另外审查 overlay 修改。
- **确认：** 成员位置、成员 SHA 和原 manifest 一致，未借机修改结果 manifest；网页如只能整包下载，就如实显示整包下载。

### E28. 新演示是 HTML，不能像历史四个 MP4 那样直接播放

- **当前实现：** 历史导入中的公开演示是 MP4；新的 portable 导出器生成 HTML，并相对引用 `../videos/` 等文件。
- **处理：** 下载并解压完整 TAR，保留目录结构后打开。只上传/下载单个 HTML 会丢依赖；把它的分享链接填入 MP4 播放字段也不会解决问题。
- **确认：** 原生视频分别能访问，完整目录的演示能加载；没有实际视频播放证明时 playback_url 保持 null。HTML 可作为下载后的可浏览报告，不能描述成已经托管的单文件视频。

### E29. 大包分片上传成功，不代表已经支持网页自动重组

- **当前限制：** 上传器单文件上限 128 MiB，可用 pack 生成分片；分片收据证明的是每一片，不是完整 TAR。存储文档的单 TAR 合并示例不能接收 chunks.json 或任一分片收据作为整个包。
- **处理：** 保留原包、分片清单与每片收据。下载时逐片核验、按清单顺序重组，再核对整包 SHA；把分片交付作为单独审查流程。
- **确认：** 重组后字节与原归档一致。当前没有自动的分片包成员登记/网页重组播放流程；不要手填“已验证”字段让示例强行通过，也不要删除唯一原包。

### E30. 公开扫描通过，但新文件其实还没被检查

- **当前实现：** `scripts/check_public.py` 从 Git index 选择文件路径，再读取工作区当前内容；未跟踪的新文件不在范围内，也不会单独检查较旧的暂存内容。只看一次绿色输出可能漏掉准备公开的内容。
- **处理：** 明确暂存打算公开的最终文件，查看 staged diff，确认这些文件没有未暂存差异，再运行公开扫描；之后如又修改，重新审查、暂存和扫描。用 `--base BASE_COMMIT` 检查已发布 manifest 不可变性，不要整包暂存私有工作目录。
- **确认：** 所有新增公共文件都在检查范围内，未包含令牌、账号身份、内部路径/IP、原始会话或私有推理。扫描是辅助，仍需人工/助手查看公开 diff。命令见 [VALIDATION.md](VALIDATION.md)。
